# Resume Quantification Rules

Use this file when the user asks for quantified resume bullets, project materials contain measurable data, or important results lack concrete numbers.

## Goal

优先生成可核证、可解释、可面试追问的量化表达。量化用于说明技术范围、执行结果或业务价值，不是给句子装饰数字。

## Evidence Levels

| 等级 | 来源 | 是否可进入投递稿 | 处理方式 |
| --- | --- | --- | --- |
| Confirmed | 用户明确提供；监控、报表、Benchmark、测试报告或正式文档直接证明 | 可以 | 记录来源并正常使用 |
| Code-verifiable | 可从代码稳定统计的 API、命令、模块、测试、协议模式、验证场景等 | 可以，但只代表项目范围 | 绑定技术价值，避免写成个人业绩或业务收益 |
| Estimated | AI 根据代码、行业经验或假设生成的点估计/区间 | 不可以 | 仅放“AI 估算候选（待核验）”，等待用户确认 |
| Unknown | 没有来源，也无法合理估算 | 不可以 | 使用 `[待补充具体数据]` 或删除数字表达 |

用户确认一个 Estimated 数字真实反映其经历后，可将其升级为 Confirmed；记录为 `user-confirmed`，不要继续标为 AI 估算。

## Quantification Priority

按以下顺序寻找数字：

1. **真实结果指标**：成功率、错误率、延迟、吞吐、QPS、成本、召回率、准确率、人工耗时、发布频率。
2. **真实规模指标**：调用量、用户数、租户数、数据量、任务量、并发数、节点数、接入系统数。
3. **测试和验证指标**：测试通过率、覆盖率、Benchmark 次数、P50/P95/P99、验证场景数、定位或修复问题数。
4. **代码可核证范围**：API 数、命令数、工具数、工作流节点数、支持协议/路由/模型数。
5. **占位或估算候选**：前四类均缺失时再使用。

真实结果指标优先于代码规模计数。直接简历稿通常保留 1-2 个最有岗位价值的量化点，不强制每条 bullet 都带数字。项目亮点素材库可以列出更多待采集指标，但不能把未核验候选写成已实现结果。

## Workflow When Metrics Are Missing

1. 先从用户材料、代码、测试和文档中提取 Confirmed 与 Code-verifiable 数字。
2. 判断缺失数字是否会明显削弱核心 bullet；普通描述不必强行量化。
3. 需要补数且用户未指定处理方式时，询问：

   `当前缺少真实结果数据。你希望保留 [待补充具体数据]，还是生成带“AI 估算、待核验”标记的候选区间，供你结合监控或实际经历确认？`

4. 用户未回复但任务要求继续时，默认使用占位符或无数字的可观察结果，不默认生成估算值。
5. 用户选择 AI 估算时，只输出估算工作表；投递版仍使用占位符或无数字版本。
6. 用户确认具体数字真实后，再生成含数字的投递版。

## AI Estimate Rules

AI 可以帮助形成候选范围，不能创造履历事实。

每个估算候选必须包含：

- 指标名称。
- 候选区间，优先区间而非精确点值。
- 推导依据和关键假设。
- 需要用户检查的监控、日志、报表或经历。
- 显著标签：`AI 估算候选，禁止直接投递`。

禁止：

- 为了让简历“好看”生成精确百分比、用户规模、营收、成本或性能提升。
- 把行业均值写成项目实绩。
- 用户未确认时把估算值放进“可直接投递”区。
- 用模糊措辞隐藏估算来源，例如“约”“近”“超过”后直接当事实使用。
- 从代码行数、提交数或依赖数推导业务影响。

## Code-Verifiable Quantification

代码计数只有同时满足以下条件才值得写：

1. 统计口径稳定且可复现。
2. 数字对应目标岗位关心的能力范围。
3. 数字与具体动作和价值绑定。
4. 不暗示用户独立完成整个仓库。

可用：

- `封装 46 项沙箱 API，覆盖生命周期、执行、文件和网络策略。`
- `适配 3 种网关路由模式，统一多入口接入行为。`
- `完成 13 类核心链路验证，定位 4 类兼容性问题。`

慎用或不用：

- `项目包含 12 万行代码。`
- `使用 36 个依赖。`
- `仓库有 800 次提交。`
- `创建 120 个文件。`

这些数字通常不能证明技术价值，也不能证明个人贡献。

## Output Shapes

### Placeholder Choice

```markdown
## 需确认/可量化补充
- 当前缺少：成功率、P95、QPS。
- 处理方式：保留 `[待补充具体数据]`。
```

### AI Estimate Worksheet

```markdown
## AI 估算候选（待核验，禁止直接投递）
| 指标 | 候选区间 | 推导依据/假设 | 请核验 |
| --- | --- | --- | --- |
| Sandbox 创建 P95 | `[候选区间]` | 基于当前生命周期和测试超时设置推断，不代表实测 | Benchmark 报告或监控面板 |
```

### Confirmed Resume Bullet

```text
在并发 [已确认数值]、目标 QPS [已确认数值] 下完成 [已确认次数] 次生命周期验证，成功率 [已确认数值]%，Sandbox 创建 P95 [已确认数值] 秒。
```

## Final Check

- 每个数字是否有 `user`、`code`、`test`、`doc`、`config` 或 `user-confirmed` 证据？
- 数字说明的是个人贡献、项目范围，还是估算候选？是否写清边界？
- 是否优先使用结果指标，而不是无意义规模计数？
- 是否把任何 Estimated 数字放进了投递稿？如果是，移出。
- 用户能否在面试中解释统计口径、时间范围和数据来源？
